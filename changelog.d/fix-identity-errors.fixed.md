- The `identity` utilities' errors say whether anything was sent and what to do next, naming the utilities the way the agent runs them (`identity--accept_invite`, through `utils`).
  - `request` with `fromFile` says why a file disk has couldn't be read and what to do: a directory, a link the mount doesn't follow, a link to a file outside the workspace, a file that changed while it was read, or a refusal that is the host's to fix. The upload receipt's new `from` says which copy went: disk's, or the workspace's where disk has no file at the path. Every successful upload carries the receipt, including one whose response was saved with `saveAs` or was binary, and a failure after the workspace's copy went out names that copy.
  - `request` with `saveAs` is refused before anything is sent when the workspace couldn't keep the response: there's no workspace, no mount has the path, it names a mount but no file, it leads out of its mount, or the mount is read-only. Before, the request went out and only then failed to save, so a write's answer was lost.
  - A response that `saveAs` stored in the workspace, with only its copy on disk failed, counts as saved, as agent-framework's `save_recent_image` counts such a file, and the receipt's new `saved.diskCopyError` gives the reason. Before, the agent read that the response couldn't be saved, and could send a write again for it.
  - A write's binary response that isn't saved no longer advises repeating the request with `saveAs`, which would send the write again. It says to pass `saveAs` with the write itself. A GET's note is unchanged.
  - A `request` that got no reply says its outcome is unknown, and to check a write before sending it again. One the service answered, whose response couldn't be read or saved, gives the status it was answered with and says that what the request changed stays changed. Before, both read "<service> request failed".
  - When the identity service doesn't give access, the message goes by its status: a 429, a 5xx, or a 200 whose reply can't be read says to try again shortly, and any other refusal points to `identity--status` and the operator. The agent reads these through `request`. The operator reads a sentence of their own in the MCPL dial's log, which a failed access repeats on every reconnect. When the identity key can't be loaded, the log names its file and the error, and the agent's message names neither.
  - `accept_invite` says what became of a registration. A 429 registered nothing, so it says to try again shortly. With no reply, or a 5xx, whether the service registered the host is unknown, and the message says how to find out without trying another name. A refusal gives the service's reason, and allows for an earlier call that may have registered the host. A registration the service answered 200 for, but this host couldn't record (its record couldn't be saved, or the reply couldn't be read), is held for the session, so `status` and access work until the host restarts, and the operator is asked to record it. A second registration while one is under way is refused.
  - A registration record that can't be read now says that whether the host is registered is unknown, and to ask the operator. Before, it read as never registered, and its remedy, registering, would be refused.
